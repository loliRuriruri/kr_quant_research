- 이는 ‘현재 응답에 자료가 없음’의 근거다. KRX 내부 배치 지연·서비스 장애·공개 일정 중 정확히 무엇 때문인지는 응답만으로 확정하지 못한다. 영구적으로 해당 날짜 자료가 없다는 뜻도 아니다.

- 네이버 가격을 KRX 일봉 대신 저장하거나 기대 날짜를 과거로 낮춰 정상 처리하지 않았다.

## 2. 발견하여 수정한 코드 결함

### A. 날짜 검증 없는 ‘있으면 받기’ 경로

`fetch_daily_maybe`는 응답 날짜를 검사하지 않았고, `fetch_daily`는 첫 행만 검사했다. 범위 수집기는 이 자료를 요청 날짜로 정규화하므로 다른 날짜/혼합 날짜가 들어오면 잘못된 일봉을 저장할 위험이 있었다.

수정: 두 경로 모두 모든 행의 날짜를 확인한다. 날짜 누락·불일치, 비정상 행 타입, 행 배열이 없는 오류 응답은 `KrxResponseError`로 거절한다. 정상적인 빈 배열만 미공개 자료로 취급한다. 실제 저장 자료가 이미 오염됐다는 발견은 아니며, 입력 계약의 결함을 수정한 것이다.

### B. 오류 종류와 재시도 정책의 혼선

이전 탐지기는 인증/형식/통신 오류를 모두 `ready=false`로 넘겼고 스마트 실행이 이를 ‘자료 미준비’로 반복 처리했다.

- 정상 빈 배열: `not_published`, 기존 제한 횟수 내 재시도.
- 타임아웃·접속 오류·HTTP 429/5xx: 응답 오류임을 기록하고 제한적 재시도.
- HTTP 401/403, 응답 형식·날짜 오류, 키 미설정: 자동 반복 중단, 설정/응답 확인 후 수동 재시도 안내.
- 시장별 행 수·실패 분류를 실행 장부에 기록한다. 외부 오류 본문을 그대로 노출하지 않는다.

### C. 실패한 작업의 완료 메시지·자동 배포 호출

`pipeline_status=failed`가 내부적으로 error가 되어도 ‘작업 완료’ 로그를 출력하고 `_maybe_publish`를 호출했다. 배포 가드가 최종 방어를 하더라도 실패한 작업이 배포를 시작하려는 것은 잘못이다.

수정: 실패 로그를 명확히 표시하고 실패한 실행에서는 자동 배포 호출 자체를 생략한다. 기존 날짜·품질 배포 가드는 유지한다.

### D. 기존 테스트의 운영 자료 접근

부분 완료 테스트가 실제 후처리/이력 함수를 호출하고 마지막 로그 한 줄만 비교해 실패했다. 새 로그가 붙으면 실패하는 낡은 단언이었다. 테스트의 후처리·이력 쓰기를 격리하고 완료 로그의 존재를 검사하도록 수정했다. 첫 실행에서 파생 캐시 준비/테스트 이력이 호출됐으며 원천 수집·공개 배포는 발생하지 않았다.

## 3. 시즌 메뉴 연동 — 실제 자료 검사

검증 스크립트: `scripts/audit_item2_integration.py`. 원시 결과: `output/item2-integration-audit.json`.

단위는 종목만이 아니라 `signal_id`(종목·패턴)와 `generation_id`다. 원본 API 배열 순서를 순위로 간주하지 않고, 실제 UI의 허용 진입 단계와 `pre_entry_rank` 기본 정렬을 적용했다. 첫 감사에서 이 정렬을 빠뜨려 불일치가 나왔으나 검사 코드를 바로잡아 재검증했다. 이를 제품 버그로 오인해 엔진 순위를 바꾸지 않았다.

- 후보 279개 신호 ID 중복 없음.
- 대시보드 TOP3와 캘린더 기본 정렬 TOP3 신호·가격 기준일·관찰 구간·저장 종가 동일.
