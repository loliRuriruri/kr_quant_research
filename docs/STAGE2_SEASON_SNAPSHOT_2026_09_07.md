# 2단계: 시즌 메뉴 사전 계산과 선정 기록 연결

작성일 2026-09-07. 작업 전 롤백 기준 `5ab116a`.

## 적용 범위

대시보드 시즌 Top 3, 시즌 탐색 목록, 오늘의 시즌 후보·테마맵, 종목별 시즌 상세를 동일한 읽기 전용 저장본으로 연결했다. Quant 점수 계산식·운영 랭킹은 변경하지 않았다. 이는 시즌 영역의 공통 선정 기록 기반이며, 전 메뉴 신호 장부와 사후 성과 검증까지 완성했다는 뜻은 아니다.

## 구조

1. 서버 시작과 live/screen/KRX/DART/smart-sync 데이터 작업 완료 후 백그라운드 준비를 요청한다. 중단된 작업은 준비하지 않는다.
2. 기본 5년 자료와 이 PC에서 사용한 기간의 자료를 갱신한다. 지원 기간은 기존 UI와 같은 0(전체), 2, 3, 5년이다.
3. 자료가 처음 없는 기간을 조회하면 계산 스레드를 요청하고 즉시 `503 + Retry-After`를 반환한다. HTTP 요청 안에서 계산 완료를 기다리지 않는다.
4. 브라우저는 준비 중 응답을 최대 15회, 3초 간격으로 재확인하고, 계속 미완료이면 안내와 재시도 버튼을 표시한다. 확정된 계산 실패는 자동 대기를 반복하지 않고 오류를 표시한다.
5. 가격·기업행위·점수·마스터·수급 입력의 파일 지문, 설정 해시, 전략/거래 적격성 코드 해시와 당일 날짜로 세대를 구분한다. 코드·입력·날짜가 바뀌면 이전 결과를 현재 결과로 쓰지 않는다.
6. 계산 전후 원천 지문이 다르거나 점수 세대 갱신 중이면 게시하지 않는다. 준비 도중 기존 완성본 파일은 보존하지만, 구세대 후보를 현재 후보로 API에서 제공하지 않는다.
7. 세대별 완성본 JSON을 원자적으로 새로 만들며 동일 이름을 덮어쓰지 않는다. 여러 프로세스가 동시에 준비해도 먼저 게시된 완성본을 재사용한다.

기존 12개월 월별 스크리너·정량 이벤트 랭킹·다른 메뉴 API의 모든 계산이 옮겨진 것은 아니다. 그 영역은 후속 사전 계산 대상이다.

## 공통 근거와 기록

- `generation_id`: 동일 입력·설정·코드·조회 기준일·학습 기간의 자료 식별자.
- `signal_id`: 세대 안의 종목·패턴·월 식별자. 목록, Top 3, 상세에 전달한다.
- `generated_at`, `selection_date`, `record_type=observed_snapshot`: 실제 이번 준비 시점의 기록. 과거 날짜의 당시 선정 신호를 소급 생성하지 않는다.
- `content_hash`: 저장 내용 무결성 확인. 디스크에서 다시 읽을 때 확인하고 손상된 파일은 사용하지 않는다.
- 기본 조건의 Top 3는 같은 공통 후보 목록의 순위로 생성한다. 필터는 순위를 소급 수정하지 않는다.
- 대시보드 상세 요청에 화면의 세대를 전달한다. 그 사이 갱신됐으면 409로 목록 새로고침을 요구하여 다른 세대의 근거를 조용히 섞지 않는다.
- 원천 경로·설정 자체는 API에 노출하지 않는다. 공개 응답에는 식별자와 시각만 전달한다.

저장 위치: `data/research_snapshots/season/`. 한 기본 5년 세대에서 3,775개 패턴, 약 34.5MB JSON을 관측했다. 생성 시점별 파일은 로컬에 남기고 Git에는 포함하지 않는다. 장기 보관 압축·보존 기간 정책은 후속 과제이며 이번에 과거 기록을 자동 삭제하지 않았다.

## 관측 결과

이번 원천 자료의 가격 기준일은 2026-09-04이다. 실시간 시세가 아니다.

- 최초 공통 저장본 준비: 103.68초. 메뉴 요청 밖의 배경 계산이다.
- 별도 새 Python 프로세스에서 동일 저장본 재사용: 0.823초.
- 이후 코드 지문 보강에 따른 새 세대 준비: 하위 계산 캐시를 재사용하여 13.545초. 최초 계산과 같은 조건의 성능 비교가 아니다.

위 측정 뒤 후보+테마 응답은 적격 후보만 전송하도록 더 줄였다. 원래 약 6.98MB의 전체 탐색 응답은 상세 탐색 API에 남아 있다. 종목 상세 지연 로딩과 전체 탐색 응답 슬림화는 후속 성능 과제다.

최종 코드로 로컬 8790 재시작 후 후보+테마 응답은 **279개 적격 패턴, 1,746,342byte**로 축소됐다(약 75% 감소). 5회 조회 409.3/410.2/768.1/421.5/706.4ms. Top3는 첫 요청 1,083.9ms, 이후 473.9/327.5/302.4/305.3ms였다. 동시 회귀검사·브라우저 실행이 있는 개발 PC에서의 관측으로 환경에 따라 달라진다.

재시작 후 브라우저에서도 동일 세대·상위 3개 선정 ID 일치, 로딩 오류 없음 확인. 화면 기록 `output/playwright/stage2-season-snapshot.png`. 검증용 8791 서버와 브라우저 세션 종료. GitHub push·공개 배포 없음.

## 검사와 제한

최종 선택 회귀검사 **98 passed / 89.98초**, Node 문법·Python 컴파일·git diff 공백 검사 통과. 기존 API 테스트는 이제 명시적 준비 단계를 먼저 실행하도록 수정했고, 캐시 동시성 테스트에는 실제 Settings와 맞는 root/output 경로를 추가했다. 제품 전체 테스트나 수익성 검증의 완료를 뜻하지 않는다.

- 저장본 재시작 재사용, 반환값 수정 격리, 동일 입력 중복 게시 방지.
- 원천 변경·계산 도중 변경 감지, 이전 세대 파일·포인터 보존.
- 저장 내용 손상 시 거부, 기간 분리, 검색 필터의 순위 보존.
- 메뉴 조회에서 연구 엔진을 호출하지 않음, 초기 미준비 503, 세대 불일치 상세 409.
- 중복 준비 요청 합치기, 데이터 작업 종료 후 예약, 취소 작업 제외.
- 기존 공개 JSON에 신규 경로가 없을 때 기존 목록+테마를 읽는 호환 처리. 새 내보내기는 API 조회 전에 명시적으로 자료를 준비한다. 실제 공개 배포는 수행하지 않는다.
- 실제 브라우저 확인은 Playwright 스킬로 수행. 인수인계 스킬로 이전 변경을 보존했다. web-perf의 Chrome DevTools MCP가 없어 해당 추적 절차는 사용하지 않았으며 CWV/INP/LCP 수치는 보고하지 않는다.

## 다음 우선순위

1. Quant 후보까지 불변 선정 기록을 확장하고 팩터 기여·제외 근거·정정 관계를 연결한다. 현재 시즌 자료의 당시 관측 저장을 미래 승률 검증으로 오인하지 않는다.
2. 선정 기록 기준 D+1/5/20 성과·비용·진입 불가를 검증한다. 시즌 연도 분리 OOS와 미래 정보 누수 검사를 진행한다.
3. 큰 탐색 응답과 남은 이벤트/월별 메뉴의 계산을 사전 계산·요약/상세 분리로 전환한다.
4. 준비 진행률·지연 사유를 실행 파이프라인에 명확하게 연결하고, 세대 변경 시 이미 열린 메뉴의 오래된 카드 표시도 더 적극적으로 갱신한다.
5. 실시간 시세는 일봉 점수와 별도 공급 경로로 연결한다. 이번 변경은 실시간 API 신규 연결이나 상시 서버 구축이 아니다.
