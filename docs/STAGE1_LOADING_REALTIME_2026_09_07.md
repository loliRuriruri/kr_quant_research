# 1단계 계산 정비·메뉴 로딩 개선 결과와 후속 계획

작성: 2026-09-07. 대상: 로컬 KR Quant Research. 공개 사이트 배포와 실시간 시세 신규 연동은 이번 작업에 포함하지 않는다.

## 결론

느림의 원인을 퀀트 엔진 하나로 볼 수 없다. 초기 화면이 불필요한 API까지 기다리는 문제, 큰 JSON 전송, 계절성 조회 중 대량 계산이 겹쳤다. 우선 화면과 조회 경로를 개선했다. 다음은 **수집 완료 후 메뉴 자료를 미리 계산하는 공통 스냅샷**이며, 그 다음 실시간 시세를 일봉 기반 점수와 별도 경로로 연결한다.

이번 범위는 기존 도입 로드맵의 1단계 핵심 계산 정비와 추가 성능 과제의 첫 묶음이다. 전체 메뉴 p95, 모든 순위 교체의 팩터별 원인 보고, 시즌 OOS 등 남은 통과 기준까지 완료했다는 뜻은 아니다.

## 1. 저장점과 검증 범위

- 작업 전 저장점: `4cc5345`. 이전 신뢰성 패치를 보존한 상세 메시지의 로컬 커밋.
- 이전 계산 비교 기준: `bd09ece`의 peer scoring 및 freshness 함수. 나머지 파이프라인·설정·입력은 동일하게 유지했다. 과거 Git 트리 전체를 그대로 실행한 비교는 아니다.
- 사용자 포트폴리오 JSON의 기존 개행 변경은 커밋 대상에서 제외한다.
- API 키·사용자 설정·공개 배포·운영 랭킹 파일을 교체하지 않았다.
- 선택 회귀검사 76개 통과(62.22초), JS 문법·Python 컴파일 통과. 전체 테스트 모음이나 투자 성과 보증은 아니다.
- 도구: 인수인계 스킬로 변경 이력 보존, Playwright 스킬로 실제 브라우저 요청·표시·실패 복구 확인. web-perf가 요구하는 Chrome DevTools MCP가 없어 해당 절차는 중단하고 Resource Timing·서버 측정으로 대체했다. CWV/INP/LCP나 운영 p95 측정값은 없다.

## 2. 실제 로딩 진단

| 관측 | 변경 전 실제 로컬 관측 | 이번 조치 |
|---|---:|---|
| 초기 watchlist 요청 | 약 10.1초 | 해당 메뉴 진입 때만 조회 |
| 대시보드 계절성 Top 3 | 약 8.5초 | 종목 표를 기다리게 하지 않고 별도 로딩 |
| 숨겨진 설정·연결 검사·배포·포트폴리오 | 초기 화면에서도 요청 | 초기 호출 제거 |
| 전체 순위 JSON | 약 2.20MB | 순위 메뉴에서 지연 조회, 압축 |
| 스마트 수급 JSON | 약 2.54MB, 조회 약 3.69초 | 압축, 메뉴 단위 성공 캐시 |
| 실패한 메뉴 | 요청 전에 로딩 완료 시각 기록 | 성공 후에만 기록, 오류·재시도 표시 |
| 전략 메뉴 | 저장 결과가 없으면 자동 계산 | 명시적 계산 버튼으로만 실행 |

패치 후 실제 데이터로 첫 종목 행 표시 약 **519ms**를 관측했다. 변경 전 동일 조건의 첫 행 측정값은 없어 개선 배수는 산출하지 않는다. 이때 상태 API 약 3.1초와 계절성 약 9.3초는 표와 독립적으로 완료됐다.

압축 전/후 실제 JSON 전송 본문:

| API | 비압축 byte | gzip byte | 절감 |
|---|---:|---:|---:|
| Top 100 | 268,835 | 41,794 | 약 84.5% |
| 전체 순위 300 | 2,199,661 | 343,300 | 약 84.4% |
| 수급 | 2,538,131 | 313,978 | 약 87.6% |

이 수치는 전송량 개선이다. 서버 처리 시간이 같은 비율로 줄었다는 의미는 아니다. 비밀 설정 응답·쓰기 요청은 압축 대상에서 제외했다.

### 계절성이 특히 느린 이유

Top 3 조회 내부에서 1,138개 종목·월 조합의 과거 가격 경로를 계산했다. 서버 재시작 때 사라지는 메모리 캐시만 있었다.

- 가격·기업행위·마스터·manifest·기준일·루트 및 계산 스키마가 같은 경우에만 재사용하는 저장 캐시를 추가했다.
- 새로운 프로세스에서 측정한 조회는 캐시 생성 약 28.4초, 저장 캐시 재사용 약 8.5초였다. OS 캐시 등 조건 차이가 있어 엄밀한 속도 비교 실험은 아니다.
- 캐시가 깨지거나 소스가 바뀌면 재계산하고, 저장 실패 시 메모리 방식으로 동작한다.
- **첫 조회는 여전히 느리다.** 근본적인 다음 조치는 조회 요청 밖에서 사전 계산하는 것이다.
- 계산 의미가 바뀌면 캐시 스키마 버전도 올려야 한다.

### 추가 적용

- 메뉴 중복 요청 합치기, 활성 메뉴만 새로고침, 로딩/오류/재시도 상태 표시.
- 숨겨진 브라우저에서 반복 조회 중단, 매크로 조회 주기를 서버 캐시와 맞춤.
- 공개 정적 화면에서 로컬 실시간 반복 조회 방지.
- 순위 데이터 기준일을 별도로 표시하여 시세와 계산 기준일을 혼동하지 않도록 정비.
- 실제 브라우저 검사: 상태 응답 지연 중에도 표 표시, 실패 후 재시도, 재방문 캐시, 전략 메뉴의 무단 재계산 방지.

## 4. 성과·설명 계산 정비

- 이벤트 초과수익률에서 명목 주가 평균을 시장지수처럼 사용하던 계산 제거.
- 명시된 벤치마크와 정확히 일치하는 관측 날짜가 있을 때만 초과수익률 산출. 현재 호출 경로처럼 원천이 없으면 미산출(null).
- 공시일 종가 이후 반응 통계는 실제 체결 백테스트가 아님을 응답에 명시. 비용·기업행위·PIT 체결 검증 완료로 주장하지 않는다.
- 중복 날짜·비정상 가격을 임의 평균하거나 0%로 채우지 않음.
- 자체 점수 구간을 STRONG_BUY 등 자동 매수 의견으로 변환하지 않고 점수 등급·부적격·자료 부족으로 분리.
- 팩터 배점 비율을 업종 백분위처럼 설명하던 화면 문구 정비. 진짜 peer 백분위·표본 상세 연결은 다음 단계.

## 5. 다음 진행 순서

### 2단계: 공통 선정 기록 + 사전 계산 스냅샷 (최우선)

수집/검증/점수/시즌 계산 완료 후 동일 `generation_id`와 `signal_id`를 가진 읽기 전용 메뉴 묶음을 만든다. 대시보드 Top 3·시즌 목록·상세는 이 자료에서 파생한다. 생성 성공 시에만 원자적으로 전환하며 조회 API는 원칙적으로 계산하지 않는다.

통과 기준: 동일 필터의 종목·순서·수치·기준일 일치, 재시도 중복 없음, 계산 중 기존 완성본 유지와 이전 기준일 표시, 새 프로세스 첫 조회에서도 사전 결과 사용. 실제 데이터로 각 메뉴 cold/warm 반복 측정 후 p50/p95 보고. 목표 응답시간은 측정 환경과 함께 합의하며 아직 달성한 값으로 표시하지 않는다.

### 3단계: 종목 선정 신뢰성 검증

고정 선정 기록의 D+1/5/20 성과와 연도 분리 시즌 OOS를 계산한다. 미래 정보·당해 미완료 구간·사후 최고가 누수를 검사하고 거래비용·진입 불가·표본 수·불확실성을 공개한다. 최고가까지 상승률을 실현 가능한 기대수익률로 부르지 않는다.

### 4단계: 실시간 시세 전용 경로

일봉 점수 계산을 틱마다 반복하지 않는다. 실시간 가격/등락은 별도 상태로 결합하고 `provider_observed_at`, `received_at`, 지연·끊김 상태를 표시한다. 기본 범위는 현재 보고 있는 종목/관심종목부터 제한적으로 제안한다. 구체적인 구독 종목 수·초 단위 주기·WebSocket/SSE 선택은 공급자 규격과 권한·호출량을 확인한 뒤 결정한다.

| 자료 | 운영 방식 제안 |
|---|---|
| 가격·호가 | 허가된 실시간 피드가 있을 때 별도 구독, 끊기면 지연 표시 |
| 투자자 수급 | 잠정/확정, 집계 구간, 제공 시각 구분 |
| Quant 점수 | 확정 일봉·사용 가능 공시 기준 배치 계산 |
| 재무공시 | 신규 공시 확인 후 갱신, 가격과 동일한 최신성 기준 사용 금지 |
| 시즌 통계 | 새 일봉/기업행위/모델 세대에 맞춰 사전 계산 |
| AI 해설 | 근거가 바뀔 때 재생성, 클릭마다 호출하지 않음 |

API가 연결됐다는 사실은 실시간 피드가 구현됐다는 뜻이 아니다. 공개 Pages의 JSON 스냅샷도 그 자체로 실시간 서버가 아니다. PC가 꺼져도 계속 운영하려면 별도 상시 백엔드와 시세 재배포 권한·비용 검토가 필요하다. 이번에는 새 유료 서비스나 배포 구조를 만들지 않았다.

### 5단계: UI/UX 재구성

- 처음에는 종목 표와 핵심 3개 요약을 우선 표시. 긴 AI 브리핑은 접거나 상세 영역으로 이동.
- 모든 메뉴의 종목 상세 드로어를 공통화하고 선정 신호·시세·반대 근거를 연결.
- 가격 시각 / 점수 기준일 / 공시 시점을 구분하고 상태 바의 좁은 폭 줄 깨짐 개선.
- 필터·검색·정렬·스크롤을 유지하고 URL로 상태를 복원.
- 미조회·수집 중·조건에 맞는 종목 없음·오류를 서로 다른 화면으로 표현.
- 대용량 표는 요약/상세 응답 분리 후 필요 시 가상 스크롤 도입. 신규 라이브러리 도입 자체를 성능 개선으로 간주하지 않음.

### 6단계: 통합 운영 검증

모든 메뉴의 실제 데이터 cold/warm·오류·재시도·서버 재시작·다중 탭을 검사한다. 로컬/공개 모드, stale 표시, 개인정보/비밀 검사와 기존 품질 게이트를 유지한 상태에서 배포 검증한다.

## 참고

브라우저 작업을 분리하고 렌더링 부담을 줄이는 방향은 [web.dev 렌더링 성능 안내](https://web.dev/articles/rendering-performance)를 참고했다. 외부 리서치 서비스 참고 항목과 원래 1~6단계는 [기존 도입 로드맵](REFERENCE_ADOPTION_ROADMAP_2026_09_07.md)에 보존한다. 본문의 후속 번호는 추가 성능·실시간 작업을 결합한 실행 순서다.
